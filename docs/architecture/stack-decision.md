# Architecture decision: preserve the existing application

The original specification named Next.js, FastAPI and PostgreSQL. The initial implementation used Node/browser JavaScript and SQLite as an available-runtime convenience, not an originally approved equivalent stack. The current owner instructions explicitly require preserving/extending this repository and avoiding unnecessary framework migration. No claim is made that a syntax build check is a Next.js build or that shared .d.ts contracts are a full TypeScript conversion.

The current model now has independent relational institution, programme, obligation, instrument, association, document/version, lifecycle, clearance, policy-history and immutable analysis/audit identities; the older per-case JSON-only limitation was addressed by additive migrations. JSON remains useful for immutable evidence/configuration snapshots and validated instrument facts. The selected storage, provider, policy and worker contracts are modular. Large server orchestration and string-rendered UI files remain maintainability debt; new capabilities use focused modules instead of a rewrite.

SQLite WAL is deliberately single-owner here. The owner lock, synchronous bounded transactions, optimistic revisions, unique constraints, atomic audit seals and tested recovery support local workflows. They do not implement independently leased distributed workers, shared storage or horizontally replicated app servers. Two bounded OCR children reuse local models. Relational graph tables satisfy current relationship queries; a graph database is not necessary.

Final local load metrics and500-case/10000-event overview limits must inform deployment planning. Do not infer production throughput from HTTP-loopback tests. PostgreSQL/shared private storage/durable distributed leases are justified if multi-process deployment, independent worker pools or workloads beyond the tested query/ownership bounds are required. They are not prerequisites merely because a workflow belongs to Phase3. Next.js/FastAPI conversion needs a concrete team/deployment/maintenance justification separate from database scaling.

Any future migration must preserve IDs, hashes, timestamps, immutable payloads, policy capsules, audit trust roots and correction/evaluation succession. Use a verified signed backup, export counts/digests, equivalent authorization/transaction contracts, backend-specific concurrency tests, parallel read comparison, rollback plan and reviewed cutover. Never overwrite the historical store or silently replace its protected audit checkpoint. No framework/database conversion or remote deployment is performed in this assignment.
