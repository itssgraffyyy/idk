# Signed local backup and isolated restore

Use `node scripts/backup.js create --source="<stopped data directory>" --output="<new backup directory>"`. The source must be stopped: a live owner lock is rejected, never removed. This command takes the same owner lock while using SQLite VACUUM INTO to include committed WAL state and copying all referenced document-version and draft blobs. It checks database integrity/foreign keys, exact object sizes/hashes, source relationships, audit signatures and MFA ciphertext. The signed manifest authenticates database/blob/checkpoint hashes, migration checksums, counts, key fingerprints and archive identity. It excludes all signing/encryption keys and service environment. Source database/blob data is unchanged. Partial failed destinations are retained for inspection; no source or existing destination is deleted.

Set `AUDIT_KEY_FILE` to the retained external signing key when using `node scripts/backup.js verify --archive="<backup directory>"`. Set `MFA_KEY_FILE` as well if the snapshot contains enrolled or pending MFA. The archive never supplies its own trusted key. Default source keys live under DATA_DIR/security unless configured otherwise; protect them separately. Losing a required key prevents authenticated recovery; no silent key or audit-root replacement exists. A separate pathname is not proof of independent custody, and mode0600 does not establish Windows ACLs.

Restore using `node scripts/backup.js restore --archive="<backup directory>" --output="<new isolated data directory>"` with the same external key variables. It verifies before copying, accepts no existing destination, rejects traversal and junction escapes, checks copied bytes again, revokes all copied sessions and appends a signed restoration audit event. `restore-receipt.json` identifies the explicit historical isolated restore. Start that copy with DATA_DIR pointing to the new directory, the retained AUDIT_KEY_FILE and MFA_KEY_FILE where needed, and AUDIT_CHECKPOINT_FILE pointing to its new `security/audit-checkpoint.json`. The original source/checkpoint is untouched.

This is an explicit isolated historical restore, not automatic production rollback approval. Supplying a newer protected production checkpoint to an older restored database fails closed; the feature does not overwrite that anchor. Coordinate real rollback, key custody and independent checkpoint retention operationally. Restore verification is not itself a successful service-start claim; tests additionally start, authenticate, retrieve original private bytes and restart the restored application. All original case/evidence/document/obligation/instrument/draft/scan rows and old audit rows remain byte-equivalent at the logical-record level; restoration adds one audit event and revokes sessions. Page layout/SQLite rowids need not match after VACUUM; domain IDs, evidence IDs, hashes and relationships do.

Scope: current local private storage, not an S3 backup implementation. Default bounds10000 referenced objects/4GiB estimated database+blob data; each private object remains at most4MiB. Unreferenced recovery/orphan files, old pre-migration database snapshots, custom storage-adapter content and deployment configuration are not bundled; retain those separately. The original source copies remain untouched. The archive is authenticated but not encrypted by this tool: use protected/encrypted backup media and environment-specific ACLs. Independent storage/custody, power-loss testing and production recovery objectives remain deployment responsibilities. Source consistency assumes cooperating writers honor the single-owner lock; manual concurrent database maintenance is not supported.
